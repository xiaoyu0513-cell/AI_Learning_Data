## 1. 项目究竟解决什么问题

输入：岗位、公司、技能、候选人以及技能依赖关系。
输出：岗位问答、图谱关系、人岗技能差距和技能提升后的匹配岗位。

项目没有训练新的大语言模型。它用本地嵌入模型编码文本，
用数据库检索证据，再调用 DeepSeek 组织答案。

三条链路要分开理解：

```text
建库：jobs.json → Neo4j 图谱
              → 岗位档案 → BGE 向量 → Milvus
                         → 中文/英文分词 → 内存 BM25

问答：用户问题 → 查询路由 → 混合检索 / 图检索 / 组合检索
                       → Document 证据 → DeepSeek → SSE → 页面

人岗：候选人技能 + 岗位技能 → 交集/差集 → 覆盖率与学习路径
```

此时应能回答：Neo4j 管关系，Milvus 管文本语义检索，BM25 管关键词匹配，
DeepSeek 管查询分析和回答表达。

## 3. 先看总调度，再看接口入口

## 4. 建库：JSON 怎样进入 Neo4j

打开 [graph_data_preparation.py](../backend/rag_modules/graph_data_preparation.py)。
从 `build_graph()` 开始，用 F12 依次进入各个 `_write_*` 方法。

```text
load_seed_data → create_constraints
              → 写分类、职级、公司、技能
              → 写岗位与岗位关系
              → 写候选人与投递关系
              → 写技能前置关系
```

数据模型包括 7 类节点、8 类关系：

```text
Candidate --HAS_SKILL--> Skill <--REQUIRES_SKILL-- Job
Candidate --APPLIED_TO--> Job --POSTED_BY--> Company
Job --BELONGS_TO_CATEGORY--> JobCategory
Job --HAS_SENIORITY_LEVEL--> SeniorityLevel
Job --HAS_RESPONSIBILITY--> Responsibility
Skill --PREREQUISITE_OF--> Skill
```

重点读 `_write_jobs()` 中的 `MERGE`：查找或创建节点，再连接已有技能等节点。
`SET` 更新属性，`MATCH` 找已有节点，`MERGE` 避免同一模式重复创建。
参数如 `$name` 由 Python 传入，而不是直接把业务值拼进查询字符串。

注意：`build_graph()` 的注释提到清空旧数据，但当前实现没有先清空图谱；
主要执行 MERGE/SET。因此不能认为删除 JSON 数据后，旧图节点就会自动删除。

数据库已启动并建库后，可以在 Neo4j Browser（http://127.0.0.1:7474）运行：

```cypher
MATCH (j:Job)-[:REQUIRES_SKILL]->(s:Skill)
WHERE j.nodeId = 'job_020'
RETURN j, s;
```

看到岗位与技能节点连起来，说明你已经把 JSON 与图结构对应起来了。

## 5. 向量和 BM25 索引怎样生成

仍在 `graph_data_preparation.py` 中打开 `build_job_documents()`。
当前是每个岗位生成一份完整档案，没有做通用 PDF 解析或长文档切块。

返回的每个 LangChain `Document` 有两部分：

- `page_content`：岗位名称、公司、地点、描述、技能、职责等可检索文本。
- `metadata`：岗位 ID、公司、分类等，供去重和证据展示使用。

然后打开 [embedding.py](../backend/rag_modules/embedding.py)：

- 模型：`BAAI/bge-small-zh-v1.5`，当前配置为 512 维。
- `encode_documents()` 编码岗位文本。
- `encode_query()` 在问题前加中文检索指令，再编码查询。
- 两种编码都归一化；嵌入模型与 DeepSeek 是两个不同的模型。
- 默认离线读取本机缓存；没有缓存时需按 README 配置联网下载。

打开 [milvus_index.py](../backend/rag_modules/milvus_index.py)：

1. `_create_collection()`：定义字段，创建 HNSW 向量索引，距离度量为 COSINE。
2. `build_vector_index()`：生成文档向量，将向量、正文和元数据写入 Milvus。
3. `vector_search()`：编码用户问题，查询相似向量，再还原成 Document。

最后打开 [hybrid_retrieval.py](../backend/rag_modules/hybrid_retrieval.py) 的 `initialize()`：
对同一批档案分词，创建内存中的 BM25 索引。
这里的中文处理是相邻中文字符组成 bigram，英文和数字通过正则提取；并未使用 jieba。

完成后应能解释：20 个岗位为什么通常对应 20 条岗位向量？为什么还要 BM25？

## 6. 问题进来后，如何选择检索策略

打开 [intelligent_query_router.py](../backend/rag_modules/intelligent_query_router.py)。

先读 `analyze_query()` 中的提示词。DeepSeek 返回 JSON，包含复杂度、关系密集度、
是否需要推理和推荐策略；`route_query()` 根据推荐策略分发调用。

| 策略 | 调用方法 | 理解示例（并不保证模型必选此策略） |
| --- | --- | --- |
| hybrid_traditional | hybrid.hybrid_search | 查岗位的描述、要求 |
| graph_rag | graph.graph_rag_search | 查候选人、技能、岗位之间的关系 |
| combined | _combined_search | 同时需要文本证据与关系证据 |

当前不是程序根据两个分数固定算出策略，而是采用模型返回的策略；
异常时通过 `_rule_based_analysis()` 按关键词降级。
`_combined_search()` 给图检索和传统检索分配名额，拼接去重，并未训练一个统一排序器。
`max_rounds` 参数尚未用于循环，不代表已实现多轮 Agent 检索。

## 7. 两种检索分别怎样实现

### 7.1 混合检索：vector + BM25 + RRF

打开 `hybrid_retrieval.py` 的 `hybrid_search()`，观察：

```text
vector_search → vector_docs ┐
                           ├→ 按岗位去重、累加 RRF 得分 → 排序 → top_k
bm25_search   → bm25_docs   ┘
```

代码中的 `rank` 从 0 开始，单路贡献为 `1 / (60 + rank + 1)`。
例如同一岗位在两路都排第 1，融合得分是 `1/61 + 1/61`。
它融合的是名次，没有直接把 BM25 分数与余弦相似度相加。
融合得分保存在 `final_score`；它不是回答正确概率，也不是人岗匹配率。

### 7.2 图检索：先理解意图，再套查询模板

打开 [graph_rag_retrieval.py](../backend/rag_modules/graph_rag_retrieval.py)：

```text
understand_graph_query → GraphQuery
                      → _entity_relation_search：直接邻接关系
                      → _multi_hop_search：多跳路径
                      → _subgraph_search：实体周围的子图
                      → Document 列表
```

模型返回实体、查询类型、深度等结构，程序执行预先编写的 Cypher 模板；
不是把任意模型生成的 Cypher 直接交给数据库。

当前实现的边界也要看懂：

- `target_entities`、`relation_types` 虽被解析，但没有真正用于约束这些检索模板。
- PATH_FINDING 复用多跳分支，没有独立保证指定终点；CLUSTERING 复用子图分支。
- 多跳按路径长度倒数评分，没有综合岗位适配性。
- 某些查询写法和返回值转换还需要真实数据库分支测试；函数名称不等于功能已验证。
- 图检索异常时会记录错误并返回空列表，不保证自动改用混合检索。

页面图谱浏览由 `services/graph_service.py` 实现，与这里的问答图检索是两条链路。
其中 `find_path()` 使用 shortestPath，别把它和问答中的 PATH_FINDING 分支混淆。

## 8. 检索证据怎样变成页面上的流式回答

按顺序打开以下文件，沿着函数调用追踪：

```text
frontend/components/chat/ChatPanel.tsx：send()
  → frontend/lib/api.ts：streamChat()
  → frontend/next.config.ts：/api 转发到 8000
  → backend/main.py：chat()
  → backend/services/chat_service.py：stream_chat()
  → backend/system.py：ask_docs()
  → router.route_query()：得到 documents、analysis
  → backend/system.py：stream_answer()
  → generation_integration.py：generate_answer_stream()
  → DeepSeek 流式输出
  → api.ts 解析 SSE → ChatPanel 按事件更新 React 状态
```

打开 [generation_integration.py](../backend/rag_modules/generation_integration.py) 的 `_build_context()`：
证据被编号为 `[1]`、`[2]`，与问题一起放进提示词。模型被要求在结论后引用编号。
这些是检索证据编号，不是联网搜索结果；提示词约束也不等于已经验证没有幻觉。

打开 [chat_service.py](../backend/services/chat_service.py)，找所有 `yield`：

| 事件 | 前端怎么处理 |
| --- | --- |
| status | 显示当前阶段 |
| route_decision | 展示检索策略与分析 |
| citations | 保存并显示证据元信息 |
| token | 追加回答片段 |
| done | 结束当前回答 |
| error | 显示错误 |

`main.py` 把事件编码成 `data: JSON\n\n`，末尾发 `[DONE]`。
前端使用 fetch 读取 POST 响应流，再按空行拆分 SSE 事件，未使用浏览器 EventSource。
模型流的一段文本不一定刚好是一个汉字或一个完整词。

前端聊天记录是组件内的 `messages`；当前后端没有把历史轮次传给模型。
因此“页面上看得到多条消息”不代表模型拥有多轮会话记忆。

## 9. 人岗分析与 What-if 是怎样算的

打开 [gap_analysis.py](../backend/rag_modules/gap_analysis.py) 的 `analyze_gap()`。

```text
查询 Candidate --HAS_SKILL--> Skill
查询 Job --REQUIRES_SKILL--> Skill
  → matched：岗位技能中，候选人已经会的部分
  → missing：岗位技能中，候选人还不会的部分
  → match_rate = 匹配技能数量 / 岗位技能数量
  → 对缺失技能反向查询 PREREQUISITE_OF，组织学习路径
```

当前必需技能和加分技能同权，也未按熟练度、学历、经验加权。
建议文案由 `_generate_recommendation()` 按分数阈值生成，不是大模型生成。
虽然 API 会经过 `_ensure_llm()` 要求 Key，但匹配公式本身没有调用 LLM。

`what_if()` 把新技能与已有技能合并，遍历全部岗位，保留覆盖率 >= 0.5 的前 10 个。
列表也可能包含本来就匹配的岗位，不能直接解释为“全部都是新增机会”。
学习路径当前从缺失技能沿前置依赖反向查找，返回顺序要结合关系方向理解，
不能未经处理就称为从基础到进阶的完整课程顺序。

对应前端是 [GapPanel.tsx](../frontend/components/gap/GapPanel.tsx)。
候选人和岗位选项目前是写在前端的数组，部分公司信息与种子数据存在差异，
因此真实业务数据以 JSON 和后端查询为准。

### 实验 C：观察完整问答（会调用外部模型）

此实验由你手动触发，会向配置的 DeepSeek 服务发送问题及检索上下文，并产生 API 用量。
此前页面与建库已经验证，但完整 AI 问答尚未完成端到端验证。

依次在以下位置打断点：

1. `chat_service.py`：`documents, analysis = self.system.ask_docs(...)`。

## 12. 阅读完成的自检

- 能从 JSON 中找出一个岗位，并说出它在 Neo4j 中连了哪些实体。
- 能解释 Document 的正文与 metadata 分别做什么。
- 能区分 embedding 编码与 LLM 生成，说明两者分别在哪调用。
- 能手算一个岗位的 RRF 排名分数与一个候选人的技能覆盖率。
- 能沿 send → API → service → router → retrieval → generation 找到对应函数。
